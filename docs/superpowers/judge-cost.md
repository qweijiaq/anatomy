# 判读成本：候选数与上下文窗口的实测

问题：一次分析的钱几乎全花在 judge（每个候选一次模型请求）。默认到底该给多少个候选、每个候选带多少源码？

两组测量分开做：候选数用 gold 集的确定性召回，不花 token；上下文窗口用真实 prompt 构造，只估算 token，不调模型。质量不能靠这两组数字回答，所以窗口默认值没有改。

## 1. 候选数 → 召回

`npm run eval:recall-at` 复用 `eval:recall` 已扫描的 29 个 gold 仓库（90 个标注点），按分数取前 N 个候选，再跑同一套 `matchGold`。

```
budget  recall   hit/gold   avg candidates
     4   38.9%   35/90    3.6
     6   44.4%   40/90    4.9
     8   48.9%   44/90    5.9
    12   53.3%   48/90    7.6
    20   53.3%   48/90    10.1
    30   55.6%   50/90    12.6
   500   61.1%   55/90    19.5
```

- 12 → 30 只多 2.3 个百分点，但候选数约 1.7 倍；模型请求和 token 同比例上升。
- 6 → 12 多 8.9 个百分点，是最划算的一段。
- 20 与 12 的命中完全相同：这个 gold 集上，多收的 8 个候选没有命中任何标注点。

**决定**：`DEFAULT_TOP_K` 从 30 改为 **12**。窗口的深度选项也按这张表对齐：6 / 12 / 30；20 不再作为一档，因为它和 12 的命中相同。`--top` 仍可要到 30/500；README 里的 61% 是全候选的上限，不是默认值的实测。

## 2. 上下文窗口 → prompt token

`npm run eval:judge-cost -- <repo> <top>` 用真实的 slice 读取和 prompt 构造，配一个只记录 token、回答 `skip` 的客户端；没有 provider 调用。

p-queue（6 个候选）：

| 窗口（before/after/deps/depHead） | 请求 | tokens | 每候选 |
|---|---|---|---|
| 12 / 60 / 2 / 60（当前） | 6 | 26,824 | 4,471 |
| 8 / 48 / 1 / 48 | 6 | 21,158 | 3,526 |
| 6 / 32 / 1 / 32 | 6 | 19,495 | 3,249 |
| 4 / 20 / 0 / 0 | 6 | 16,826 | 2,804 |

quick-lru（6 个候选）：

| 窗口 | tokens | 每候选 |
|---|---|---|
| 当前 | 20,892 | 3,482 |
| 8 / 48 / 1 / 48 | 19,489 | 3,248 |
| 6 / 32 / 1 / 32 | 17,845 | 2,974 |
| 4 / 20 / 0 / 0 | 16,794 | 2,799 |

- 紧窗口在 p-queue 上省 27%，在 quick-lru 上只省 15%：文件大小和依赖数量决定收益，不能用一个比例承诺。
- 4/20/0 省 37%，但只给候选前后 24 行、且完全不看依赖。对"决定发生在导入/调用边界"的仓库，这很可能删掉证据本身。

**决定**：窗口默认暂不改。它直接影响模型能不能看到做出判断的那几行，而上面只有成本、没有质量。

### 真实模型 A/B：current vs tight

同一仓库 `sindresorhus/p-queue`、同一 6 个候选、同一模型、关闭缓存；两次都跑完整流程。

| | current（12/60/2） | tight（6/32/1） |
|---|---|---|
| 学习点 | 5 | 4 |
| 证据 | 10 条 / 丢弃 0 | 11 条 / 丢弃 2 |
| 取证率 | 100% | 100% |
| 调用 | 7 | 7 |
| 输入 tokens | 17,971 | 12,994（-27.7%） |
| 输出 tokens | 20,796 | 21,154 |
| 总 tokens | 38,767 | 34,148（-11.9%） |

质量差异：tight 丢掉了 "head 偏移 + 惰性压缩把出队降为摊还 O(1)" 这一条，是 priority queue 里最实质的设计决定；同时有 2 条证据在窗口外被丢弃。也就是说，输入 token 省了 28%，但输出反而略多，总成本只省 12%，代价是一个关键学习点和更少的可核对证据。

**结论**：tight 不作为默认。它省下的 12% 不足以抵消丢掉的决定。下一步如果继续降本，应测 `medium`（8/48/1），并且至少在 3–5 个不同形状的仓库上重复，单仓库的结果只能算方向。

复现：

```bash
ANA_JUDGE_WINDOW=current ANA_NO_CACHE=1 <start the app or CLI>
ANA_JUDGE_WINDOW=tight   ANA_NO_CACHE=1 <start the app or CLI>
```

`ANA_JUDGE_WINDOW` 接受 `current` / `medium` / `tight` / `minimal`；未知名字会报错而不是静默回退。`ANA_NO_CACHE=1` 关闭同树缓存，否则第二次会直接复用第一次的判读。

## 3. 复现

```bash
npm run eval:recall-at
npm run eval:judge-cost -- https://github.com/sindresorhus/p-queue 6
```

召回是确定性的；token 是 `estimateTokens` 的上界，会略高于账单。两者都不调用模型。
